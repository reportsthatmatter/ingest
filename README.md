# @rtm/ingest

PDF → Markdown for public inquiry reports, deterministically.

PDF → Markdown, deterministically. The same inputs always produce the same
output, so a report can be regenerated by anyone, at any time, from its own
definition.

Used by [reportsthatmatter.org](https://reportsthatmatter.org). Architecture
and the reasoning behind it live in the site repo:
[`docs/plans/2026-08-28-ingestion-architecture.md`](https://github.com/reportsthatmatter/reportsthatmatter/blob/main/docs/plans/2026-08-28-ingestion-architecture.md).

## Install

```json
"@rtm/ingest": "github:reportsthatmatter/ingest#v0.1.0"
```

A git dependency, not a submodule: pnpm fetches it into `node_modules` pinned
to that tag, and each consumer adopts a new version deliberately. That is what
makes "a report adopts pipeline improvements on its own schedule" real rather
than aspirational — nothing arrives unannounced.

## The shape

```
<report>/ingest.ts         the report's own pipeline — what it declares
        │
        ▼
  acquire → extract → segment → structure → render
        │       │        │          │          │
   volumes,  poppler   page      blocks     full.md
   checksums           passes    + geometry  baseline.json
                                             fidelity.md
```

Every page and every block carries `{ volume, pdfIndex, printed }`, so a
review note can say *Vol 2 · PDF p.412* rather than a flat index into a
document that does not exist as one file.

## What a pass is

One named decision about how to read a source. A report composes them:

```ts
export default pipeline({
  id: "uk-leveson-inquiry",
  repo: "../uk-leveson-inquiry",
  volumes: [{ path: "archive/0780_i.pdf", sha256: "…" }, …],
  passes: [geometry("per-volume"), runningFurniture()],
});
```

**A pass never takes a regex or a pattern.** It selects among implemented,
tested behaviours. The moment a report's definition can express a pattern, it
has become a second parser with no tests of its own.

A report that genuinely needs something bespoke writes its own pass in its own
file. That is the escape hatch, and it is a staging area rather than a
destination: **when a third report needs the same pass, move it in here.** If
two reports independently fork the same pass, that is the signal to fix the
shared one, not to accept the fork.

## The rule about where a fix goes

| | |
| --- | --- |
| Holds for every document in the corpus | a shared pass, here |
| A property of *this source* the parser cannot infer | a pass the report declares |
| A judgement about *this document's text* | `corrections.yaml` (not built — #106) |

If you are writing a correction to undo something the parser did, you needed a
different pass or a bug fix.

## Checking your work

```bash
pnpm ingest run <id>        # rebuild one report from its definition
pnpm ingest verify          # fidelity gates against the real source PDFs
pnpm ingest check           # has any report's output moved?
pnpm ingest baseline <id>   # accept a move, after reading the diff
```

`pnpm ingest check` is the corpus regression signal, and it runs in the site
repo's `verify.sh`. A change that moves any report's output fails until its baseline
moves with it — the whole corpus regenerates in about five seconds, so there
is no excuse for not knowing. It exists because a fix aimed at one report
once changed three others silently.

Two tiers of test sit under it here: synthetic unit fixtures in
`tests/pipeline.test.ts`, and **golden page fixtures** in
`tests/fixtures/pages/` — real pages from the corpus, chosen for being hard.
Every synthetic test passed while a real defect shipped; that is what the
golden pages are for, and why they live with the library rather than with the
site.

```bash
pnpm test        # unit + golden page fixtures
pnpm typecheck
pnpm build       # dist/, what consumers import
```
